# РОЗДІЛ 1. АНАЛІЗ АНАЛОГІВ ТА ТЕХНІЧНЕ ЗАВДАННЯ

## 1.2 Аналіз існуючих аналогів

Для аналізу обрано три системи, кожна з яких покриває одну з функціональних складових ParkOver: Parkopedia — агрегація даних про зайнятість паркувальних місць із гетерогенних джерел; SpotHero — бронювання паркувальних місць з онлайн-оплатою; Nwave — сенсорний збір даних про зайнятість. Опис зосереджено на продукті як інженерній системі: архітектурний патерн і масштабованість, протоколи передачі даних, стек даних і механізми консистентності, критичні інженерні обмеження (Technical Bottlenecks). Внутрішня архітектура комерційних продуктів публічно не розкривається, тому опис ґрунтується на відкритих джерелах: інженерних блогах, документації API, вакансіях компаній, технічних специфікаціях (datasheet) і публічних репозиторіях. Твердження, підтверджені джерелом, викладено з посиланням на це джерело; інженерні висновки, зроблені на основі відкритих даних, подано з використанням формулювань «імовірно» та «можна припустити», що відокремлює їх від підтверджених тверджень; дані зі сторонніх (не первинних) джерел супроводжено відповідним застереженням; відомості, які у відкритих джерелах не розкрито, зазначено окремо.

### 1.2.1 Parkopedia

Глобальна платформа агрегації даних про паркування (статичні дані, динамічна доступність, транзакції) для автовиробників, навігаційних сервісів і мобільних застосунків. З 13.02.2025 входить до групи Arrive (колишня EasyPark Group) [1].

**Архітектурний патерн і масштабованість**

За даними вакансії Senior Backend Engineer, платформа описується як така, що базується на PHP, MySQL та AWS; роль передбачає повний цикл розробки RESTful API і вебзастосунків, що працюють під навантаженням в AWS, та досвід з IaC (Terraform/CDK/CloudFormation) [2, 3]. Вакансія Software Engineering Manager, Client Engineering, вказує стек PHP, Laravel, AWS, Redis і SQL. У ній описано внутрішній контур збору даних: iOS-застосунок і вебсайт команди Data Operations; дані зберігаються в AWS і віддаються B2B-клієнтам через API; також згадано модернізацію кодової бази [4]. Контур In-Car Payments побудовано як serverless: команда In-Car Payments Engineering підтримує інфраструктуру карткових платежів на TypeScript, Node.js та AWS (Lambda, API Gateway, DynamoDB) з дотриманням PCI DSS [5], а адмін-панель шару оркестрації платежів розробляється на React і TypeScript [6]. На рівні групи Arrive вакансія Senior Backend Engineer – PHP (2026) описує проєктування мікросервісів на PHP 8.4/Laravel та асинхронні патерни на SQS [7]; чи стосується це ядра Parkopedia, у відкритих джерелах не розкрито.

Можна припустити, що платформа гетерогенна і поділена за продуктовими лініями: ядро даних становлять Laravel-застосунки на MySQL; платіжний контур — окремий serverless-контур; Data Science-контур працює на Python/Spark [8]. Вплив на масштабованість, імовірно, такий: читання статичних даних (POI, тарифи) кешується і масштабується горизонтально; запис у реляційне ядро масштабується переважно вертикально; платіжний контур масштабується еластично завдяки Lambda з обмеженнями serverless-моделі (cold start, ліміти конкурентності).

**Протоколи передачі даних**

Зовнішній інтерфейс — RESTful API або feed із геоприв'язкою за галузевими стандартами [9, 10]. Публічного self-service developer portal немає; доступ надається ліцензованим партнерам (OEM, навігаційні компанії) [15]. Метод автентифікації, формат feed і частота оновлень у відкритих джерелах не розкриті. Платіжна платформа відповідає PCI DSS [5, 11]; в EV-платежах роль merchant виконує партнер (Plugsurfing) [12].

Імовірно, внутрішня взаємодія реалізована як синхронний REST (у платіжному контурі — через AWS API Gateway [5]) із чергами SQS для асинхронних задач [7]. Ознак gRPC, GraphQL чи WebSocket для клієнтів не виявлено. Для OEM імовірною є pull-модель: головний пристрій або хмара OEM періодично опитує REST API.

**Стек даних і консистентність**

За даними вакансій, у платформі використовуються такі сховища: MySQL — реляційне ядро [2]; Redis — кеш [4]; DynamoDB — платіжний контур [5]; MongoDB і OpenSearch згадано у вакансіях групи [7]. Data Science-контур щодня обробляє мільярди сенсорних точок даних на Python і Apache Spark; свіжість даних для API зафіксована як вимога [8]. Динамічну доступність формують кілька джерел: датчики і шлагбауми паркінгів, Floating Car Data (FCD), події Park-In/Park-Out (PIPO) від підключених автомобілів, комп'ютерний зір, ground-truth спостереження; над ними працюють ML-моделі, що прогнозують ймовірність знайти місце та очікувану частку вільних місць [13].

Можна зробити висновок, що дані про зайнятість є ймовірнісною оцінкою, а не виміряним станом системи, тому для них ідеться про точність і свіжість, а не про модель консистентності. Транзакційна консистентність потрібна в платіжному контурі; узгодженість платежу і бронювання між окремими сервісами, імовірно, забезпечується прикладною логікою. Гарантія місця під час бронювання [14], імовірно, залежить від систем операторів.

**Technical Bottlenecks**

1. Свіжість і точність даних. За оцінкою Parkopedia, дані про доступність у реальному часі генерують лише близько 5 % позавуличних локацій; ці дані можуть бути неточними або кількахвилинної давності [13]. Основним «датчиком» системи є ML-прогноз.
2. Залежність від ручного збору. Статична база підтримується командою операторів даних за допомогою внутрішніх інструментів обстеження [4]. Масштабування покриття, імовірно, лінійно залежить від людських ресурсів і партнерств.
3. Гетерогенність стеку і технічний борг. Аналіз вакансій дає змогу припустити, що паралельно існують PHP/Laravel, Node.js/TypeScript (serverless), Python/Spark і Go [2–8]. Вакансії згадують модернізацію кодової бази і перехід до мікросервісів [4, 7]. Після інтеграції в групу Arrive, імовірно, додається міжплатформний інтеграційний борг [1].
4. Pull-модель доставки. Можна припустити, що відсутність публічного push-каналу (WebSocket, MQTT, webhooks) для OEM підвищує затримку оновлень і навантаження від опитування.

### 1.2.2 SpotHero

Онлайн-платформа бронювання місць у паркінгах операторів (США, Канада) з інтеграцією систем операторів. 23.02.2026 Uber оголосив угоду про купівлю SpotHero; закриття очікувалося в першому півріччі 2026 р. за умови регуляторних погоджень [16]; фінансові умови не розкривалися [17]. Стек описано за джерелами 2022–2023 рр. і кар'єрною сторінкою компанії.

**Архітектурний патерн і масштабованість**

За даними кар'єрної сторінки компанії, backend являє собою моноліт на Django/Python/PostgreSQL, який переводять у модульний моноліт за принципами DDD; окремі домени (зокрема Search) виділено в сервіси на JVM/Kotlin і Go; інтеграції з операторами написано на .NET Core з поступовим переходом на Kotlin [18]. Інфраструктура: розміщення — AWS і Kubernetes; розгортання — Terraform і Helm; CI/CD — ConcourseCI; моніторинг і alerting — Prometheus, Alertmanager, VictorOps; роботи з multi-region лише починаються [18]. Команда Platform Engineering переносить функціональність із Python-моноліту в Go-застосунки [19]; для Go-сервісів існує спільна бібліотека `spothero/tools` [22, 23].

Можна припустити, що патерн міграції — strangler fig. Спільна БД PostgreSQL, імовірно, лишається точкою зв'язності. Горизонтальне масштабування обмежене stateless-екземплярами (pods) Django в Kubernetes; PostgreSQL масштабується переважно вертикально. З огляду на те, що роботи з multi-region лише починаються, розгортання історично, імовірно, було однорегіональним.

**Протоколи передачі даних**

Асинхронна взаємодія реалізована через Kafka, синхронна взаємодія між сервісами — через gRPC [18]. Пакет `spothero/tools/kafka` містить клієнт Schema Registry і (де)серіалізацію Avro [22]. На Kafka побудовано платформу реплікації даних між середовищами [19]. Integrations Squad підтримує різнорідні протоколи операторів і вимірює uptime їхніх API; для API транзакційних даних оператора SP+ розгорнуто сервіс Integration Circuit Breaker [20]. За даними сторонніх джерел [25, 26], зовнішній Partner API — REST (`/v2`), доступ лише партнерський; ліміти запитів і webhook-схеми узгоджуються індивідуально. Виробники PARCS-обладнання інтегрують передплачені резервації SpotHero через власні хмарні API [27].

**Стек даних і консистентність**

Сховище OLTP — PostgreSQL [18]. Аналітичний контур: Redshift, Trino, Hive/Iceberg, Spark, Airflow, Kafka Streams/Connect [21]. Відкритий (архівований) репозиторій `tieredcache` реалізує дворівневий кеш: in-memory BigCache і кластерний Redis [23]. Команда Platform Engineering скоротила затримку поширення даних інвентарю з 5 с до 50 мс; за даними компанії, це на 98 % знизило ймовірність помилок через race conditions під час купівлі, а трафік за той період зріс у 20 разів [19]. За даними FAQ, SpotHero фізично не утримує конкретне місце під кожну резервацію, а відстежує рівень інвентарю разом з операторами [24].

Можна зробити висновок, що між SpotHero і системою оператора діє eventual consistency: продається квота, а не фізичне місце. Конкурентний доступ до квоти всередині SpotHero, імовірно, контролюють транзакції PostgreSQL. Розбіжність між квотою і фактичною заповненістю (drive-up клієнти, абонементи) на рівні архітектури не усувається. Згадка про race conditions [19] підтверджує, що вікно неузгодженості скорочено, але не ліквідовано.

**Technical Bottlenecks**

1. Overbooking. Політику неутримання місця підтверджено компанією [24]. За даними сторонніх джерел [28], користувачі скаржаться на відмову гаража прийняти резервацію через заповненість; це можна розглядати як симптом відсутності зворотного зв'язку від фізичної зайнятості.
2. Залежність від legacy-систем операторів. Знадобилися circuit breaker, моніторинг uptime API операторів і підтримка багатьох протоколів [20].
3. Технічний борг моноліту. Django-моноліт зі спільною PostgreSQL перебуває в багаторічній міграції (Python → Go/Kotlin; .NET Core → Kotlin) [18, 19].
4. Масштабування і регіональна відмовостійкість. Двадцятикратне зростання трафіку [19] і лише початок робіт з multi-region [18] вказують на те, що однорегіональне розгортання, імовірно, обмежувало доступність.

### 1.2.3 Nwave

Вертикально інтегрована IoT-платформа моніторингу зайнятості паркувальних місць: власні датчики, мережа базових станцій, хмарний backend і API для інтеграторів.

**Архітектурний патерн і масштабованість**

Система вертикально інтегрована і має три рівні: (1) датчики зайнятості; (2) базові станції або LoRaWAN-шлюзи; (3) хмарний backend з аналітикою, консоллю й API [29, 30]. Хмара приймає трафік базових станцій як Raw messages; сервіс RTA (Real Time Availability) формує поточну зайнятість, Session Logger — паркувальні сесії [39]. За даними сторонніх джерел [35], чутливі елементи датчика — магнітометр, датчики температури і близькості (TTN Device Repository, модель G4 FM). У власній технічній специфікації Nwave тип чутливого елемента не вказано [32]; температура передається в щодобовому heartbeat [34]. Базова станція власного протоколу гібридна: STM32F7 оцифровує й фільтрує сигнал, x86 виконує демодуляцію і корекцію помилок [30]. Канал «станція → хмара» захищено шифруванням AES-256 VPN з компресією [29].

Можна обґрунтовано припустити, що хмарний backend Nwave принаймні частково розміщено в AWS. Підставами для цього є такі факти: за документацією GraphQL Occupancy API V2 підписки працюють через той самий WebSocket-транспорт, що й стандартні real-time підписки AWS AppSync, а схема використовує AppSync-специфічний скалярний тип `AWSDateTime` [37]; посібник Nwave описує розгортання RabbitMQ-брокера клієнта в Amazon MQ [38] (слабший аргумент, оскільки він стосується інфраструктури клієнта). Пряму декларацію постачальника хмарної інфраструктури у відкритих джерелах не розкрито [31].

Імовірно, backend подієво-керований: на це вказують AMQP-канал доставки, збагачення сирих подій у сесії паркування і агрегування зайнятості окремим сервісом Occupancy Aggregator [36, 37]. GraphQL-шар на AppSync є керованою serverless-компонентою: масштабування забезпечує AWS, ліміти задає постачальник рішення. Масштабованість приймання даних, імовірно, визначається радіоємністю базових станцій.

**Протоколи передачі даних**

*Рівень пристрою.* Датчики використовують LPWAN-протоколи Weightless-N, Sigfox і LoRaWAN 1.0.3 [33–35]. За технічною специфікацією виробника, LoRaWAN Class B заявлено для модифікацій 3.10 і 4.5 серії Base та для Flush Mount [32]; водночас модель G4 FM у TTN Device Repository зареєстровано як Class A [35]. Підтримується Bluetooth 5.1 з Secure Driver Identification; дальність у місті — до 3 км [32]. Weightless-N — вузькосмугова DBPSK-модуляція в субгігагерцовому неліцензованому діапазоні, переважно uplink [30]. LoRaWAN-версія не використовує ADR; heartbeat із зарядом батареї і температурою передається раз на 24 год [34]. Канал «датчик → станція» шифрується блоковим шифром Speck [29].

*Рівень «хмара → клієнт».* Задокументовані типи API, використані технології, властивості та обмеження подано в таблиці 1.1.

Таблиця 1.1 – Інтерфейси доставки даних Nwave рівня «хмара → клієнт»

| API | Тип | Технологія | Задокументовані властивості та обмеження |
| --- | --- | --- | --- |
| HTTP Caller | Push | HTTP (webhook за шаблоном) | Під час недоступності клієнта — до 9 повторів (10 спроб) з інтервалами ≈30 с – ≈5 хв, ≈25 хв загалом; відповіді 4xx не повторюються; неупорядкована доставка [36] |
| RabbitMQ RTA & Sessions | Push | AMQP | FIFO-доставка; брокер розгортає й експлуатує клієнт, з'єднання через TLS (порт 5671) [36, 38, 40] |
| REST Occupancy | Pull | HTTP REST | Відповідь менше ніж за 1 с; не підтримує оновлення зайнятості в реальному часі [36] |
| Parking Analytics API | Pull | HTTP REST | Звіти за період із фільтрацією та групуванням [36] |
| GraphQL Occupancy (V2) | Push & Pull | GraphQL, підписки через WebSocket-транспорт AppSync | Агрегація за зонами, рівнями, групами; геопросторовий фільтр за радіусом; два типи підписок (snapshot / updates); ліміт 300 запитів / 5 хв [37] |

Документація розрізняє Direct-повідомлення (сирі події: Status Change, Heartbeat, User Registration) і Smart-повідомлення (Group Availability, Parking Sessions), які формує backend з автокорекцією втрачених повідомлень і дедуплікацією [36].

**Стек даних і консистентність**

Конкретні СУБД Nwave у відкритих джерелах не розкрито. Контракт API (координати позицій; ієрархія «проєкт → зона → рівень → група → позиція»; геопросторові підписки; історичні звіти) [36, 37] дає підстави припустити використання гео- або реляційного сховища топології та сховища часових рядів для подій. На рівні подій задокументовано такі механізми цілісності: `message_trace_id`; лічильник сесій `parking_session_iterator` (0–7) для виявлення пропусків; `heartbeat_message_counter`; `correction_counter` і `partial_end` для ретроспективної корекції; дедуплікація для нерозмічених місць [36]. Session Logger відфільтровує зайнятості коротші за 60 с на open bay (нерозмічених місцях) [39].

Можна зробити висновок, що модель консистентності — eventual consistency з ретроактивною корекцією. Через переважно односпрямоване радіо стан місця може бути тимчасово хибним у разі втрати uplink-пакета. Добовий heartbeat [34] обмежує «застарівання» стану 24 годинами за відсутності подій.

**Technical Bottlenecks**

1. Енергобюджет. Ресурс 9–10 років задекларовано для профілю 20 сесій на добу [32, 33]. Батарея Li-SOCl2 замінна, ємність залежить від моделі: 10 800 мА·год [33] або 13 500 мА·год [32]. На місцях з високою оборотністю фактичний ресурс пропорційно менший, а заміна батареї вимагає фізичного обслуговування кожного датчика.
2. Затримка детекції. Джерела розходяться: 12 с [30], 3–5 с для моделі G4 FM [35], менше 7 с за власною технічною специфікацією [32]. Це нижня межа «реального часу» для будь-якої системи на цих датчиках.
3. Ліміт GraphQL API. Не більше 300 запитів за 5 хв з одним токеном; у разі перевищення API повертає помилку до кінця п'ятихвилинного інтервалу [37]. Для клієнтських застосунків з одним токеном це жорстка верхня межа пропускної здатності pull-запитів.
4. Обмежене вікно повторної доставки HTTP Caller. Повтори обмежені 9 спробами протягом ≈25 хв, відповіді 4xx не повторюються [36]. Якщо endpoint клієнта недоступний довше або відповідає 4xx через помилку конфігурації, події для нього, імовірно, втрачаються. Порядок доставки не гарантований [36].
5. Перенесення експлуатації брокера на клієнта. Для надійного AMQP-каналу клієнт сам розгортає й експлуатує RabbitMQ-брокер з TLS на порту 5671 [36, 38, 40]. Посібник для Amazon MQ пропонує для простоти single-instance-брокер, тобто без кластерної відмовостійкості [38].
6. Детекція відмов інфраструктури. Базова станція вважається offline після 20 хв без ping [39]. Протягом цього вікна відмова станції не фіксується, і дані зайнятості для її зони можуть бути застарілими.
7. Радіопокриття і vendor lock-in. Для роботи системи потрібні базові станції з живленням і backhaul [30]. Можна припустити, що Weightless-N формально відкритий, але фактично використовується насамперед Nwave; розширена функціональність (SDI, Smart-сесії) прив'язана до хмари постачальника [32, 36], а GraphQL-шар — до AWS AppSync [37].
8. Точність детекції. Заявлена виробником точність — 99,7 % [32, 35]; незалежних перевірок у відкритих джерелах немає.
9. Відсутність транзакційного домену. Бронювання, ціноутворення і платежі в продукті відсутні [29, 36]; ця логіка, імовірно, повністю перекладається на інтеграторів.

### 1.2.5 Аналітичний висновок

Порівняльний аналіз Parkopedia, SpotHero та Nwave показав, що жодне з розглянутих рішень не поєднує у повному обсязі свіжість даних про зайнятість, гарантії узгодженості бронювання та незалежну масштабованість функціональних контурів, а обмеження аналогів мають архітектурний та інфраструктурний характер. Parkopedia поєднує гетерогенний стек (PHP/Laravel, serverless-контур платежів, Python/Spark) з реляційним ядром на MySQL, яке імовірно масштабується переважно вертикально, і pull-моделлю доставки даних без виявленого публічного push-каналу. Дані реального часу охоплюють лише близько 5 % позавуличних локацій і можуть бути кількахвилинної давності, а решту покриває ML-прогноз, тому для більшості локацій зайнятість є ймовірнісною оцінкою, що обмежує точність і свіжість даних. Додатково зберігається залежність від ручного збору даних. SpotHero зберігає моноліт Django зі спільною базою PostgreSQL, яка є точкою зв'язності доменів, а перехід до модульного моноліту за патерном strangler fig є еволюційним виправленням, а не архітектурною основою. Істотнішим обмеженням є те, що продається квота, а не фізичне місце: узгодження із системами операторів має характер eventual consistency, що спричиняє overbooking, а зменшення затримки поширення інвентарю з 5 с до 50 мс не усунуло race conditions повністю. Nwave як вертикальний IoT-стек вирішує задачу детекції, проте доставка подій через HTTP webhooks відбувається без гарантії порядку з повторами до ≈25 хв, відмова базової станції фіксується лише через 20 хв, а виклики GraphQL API обмежено лімітом 300 запитів / 5 хв на токен. До цього додаються vendor lock-in на власне обладнання й хмару та відсутність функцій бронювання й оплати, тож рішення є постачальником даних, а не платформою управління паркуванням.

Архітектура ParkOver відповідає на частину цих обмежень такими проєктними рішеннями. Подієво-кероване ядро (MQTT → RabbitMQ з Publish/Subscribe через MassTransit) і push-доставка змін клієнтам через SignalR (WebSocket) з Redis backplane замінюють pull-модель, тому затримку оновлення визначає шлях «датчик → брокер → клієнт», а не період опитування. Вибір RabbitMQ замість Apache Kafka обґрунтовано тим, що обсяг подій не потребує журналу з тривалим зберіганням і повторним читанням, а RabbitMQ нативно підтримує протокол MQTT. ParkOver приймає події від будь-якого джерела, що публікує їх у визначеному форматі через MQTT безпосередньо або через шлюз-адаптер, а програмний симулятор відтворює цей формат, чим знижується залежність від обладнання конкретного постачальника, властива Nwave. Для майданчиків без датчиків застосовано зважену оцінку за паркувальними сесіями та спостереженнями, що спирається на прямі дії водіїв із контрольованою достовірністю (рейтинг довіри, часове зниження ваги). Принцип Database per Service у поєднанні з шістьма сервісами за бізнес-доменами усуває зв'язність доменів через спільне сховище, властиву SpotHero. У сервісі зайнятості CQRS явно розділяє модель читання (Redis) і модель запису (PostgreSQL), а не додає кеш над спільною схемою, що дає змогу оптимізувати кожну модель під власний профіль навантаження. Exclusion constraint у PostgreSQL виключає на рівні сховища подвійне цифрове бронювання одного місця на перетині часових інтервалів. Розподілені операції (бронювання, оплата, нарахування лояльності) координуються оркестрованою Saga з компенсуючими транзакціями; Transactional Outbox забезпечує атомарність зміни стану та запису події до outbox, а отже гарантовану публікацію за семантики at-least-once (сама публікація виконується асинхронно), а ідемпотентні обробники забезпечують коректність за повторної доставки.

Проєктом передбачено Retry і Circuit Breaker для зовнішніх викликів (LiqPay) та Token Bucket rate limiting; розгортання орієнтовано на Azure Container Apps з автомасштабуванням KEDA, декларативний опис інфраструктури (OpenTofu) і спостережуваність (OpenTelemetry, Prometheus, Grafana, Jaeger). Зазначені рішення досягаються ціною архітектурних компромісів. По-перше, оркестрована Saga забезпечує лише eventual consistency: строга гарантія унікальності бронювання обмежена межами БД сервісу бронювання, а міжсервісні стани узгоджуються із затримкою та через компенсації. По-друге, поєднання брокера, Outbox, Saga й окремої БД на кожен сервіс підвищує складність експлуатації та налагодження (розподілене трасування, відтворення збоїв, версіонування контрактів подій). По-третє, покриття даними обмежене майданчиками з датчиками та достатньою активністю водіїв, тоді як Parkopedia завдяки прогнозній моделі забезпечує глобальне покриття. По-четверте, затримка детекції датчиків (одиниці секунд) є зовнішнім обмеженням, яке архітектура ParkOver не усуває, а лише не збільшує за рахунок опитування. По-п'яте, exclusion constraint гарантує унікальність лише цифрового бронювання: фізичне зайняття заброньованого місця стороннім автомобілем фіксується датчиком, але не запобігається, тому розрив між бронюванням і фізичним станом місця ParkOver не усуває. По-шосте, кожна база даних PostgreSQL також масштабується переважно вертикально, а Database per Service і модель читання в Redis лише пом'якшують це обмеження. По-сьоме, розгортання в одному регіоні, спільне з SpotHero, та залежність від сервісів Azure зберігаються, оскільки опис інфраструктури в OpenTofu лише частково знижує прив'язку до хмари. Отже, виявлені недоліки аналогів і зазначені компроміси формують вихідні вимоги до проєктованої системи, а визначення меж bounded contexts, контрактів подій, сценаріїв Saga, моделей даних та способів пом'якшення цих компромісів становлять предмет Розділу 2 («Проєктування»).

## Постановка задачі та формування вимог

Модель As-Is, на основі вузьких місць якої сформовано цільову модель і вимоги, наведено в документі Розділу 1 (посилання — у [README.md](README.md)). Нумерація таблиць і джерел продовжує нумерацію підрозділу 1.2.

### Опис концептуальної моделі цільового стану (To-Be)

Цільовий стан побудовано як хмароорієнтовану подієво-керовану платформу. Серверна частина складається з шести сервісів: Identity, Parking Catalog, Occupancy, Booking, Payment і Loyalty. Кожен сервіс розгортається як окремий застосунок Azure Container Apps з автомасштабуванням KEDA [41].

Інфраструктура платформи:
- **Дані.** Кожен сервіс володіє власною схемою в PostgreSQL із розширенням PostGIS.
- **Обмін подіями.** Сервіси обмінюються доменними подіями через RabbitMQ. Події публікуються за шаблоном Transactional Outbox, тобто подія записується в одній транзакції з бізнес-даними, а споживачі обробляють її ідемпотентно [42].
- **Кеш і доставка змін.** Redis використовується як кеш довідникових даних і знімків зайнятості. Він також є backplane для SignalR, через який зміни доставляються клієнтам при кількох репліках сервісу [43].
- **Автентифікація.** Сервіс Identity забезпечує автентифікацію за OpenID Connect і зберігає профіль водія з транспортними засобами та номерними знаками.

Перехід від As-Is до To-Be ґрунтується на чотирьох архітектурних рішеннях.

**Гібридний моніторинг зайнятості.**

*Майданчики з датчиками.* Сервіс Occupancy приймає події датчиків (у проєкті — від симулятора) через MQTT 5.0 із QoS 1 [44]. Кожен датчик періодично надсилає контрольний сигнал (heartbeat). Якщо сигналу немає довше за два інтервали, місце переходить у стан UNKNOWN, а майданчик автоматично перемикається на оцінку за сесіями та спостереженнями водіїв. Так усувається сценарій SFpark, у якому через відмову датчиків дані стали недоступні [45]. Дані датчика звіряються з активними паркувальними сесіями. Розбіжності враховуються метрикою `occupancy_conflict_ratio`, що компенсує похибку виявлення датчика (4 % змін стану [46]).

*Майданчики без датчиків.* Заповненість зони оцінюється за двома джерелами: активними паркувальними сесіями та спостереженнями водіїв. Спостереження приймається до оцінки лише після перевірки геолокації автора щодо розташування майданчика. Внесок спостереження в оцінку визначається двома чинниками:
- рейтингом довіри автора, який підвищується, коли спостереження підтверджують інші водії або датчик, і знижується при спростуванні;
- часом, що минув від спостереження: що давніше спостереження, то менша його вага.

Параметри алгоритмів визначаються на етапі проєктування: допустима відстань під час перевірки геолокації, функція і швидкість зниження ваги, правила зміни рейтингу довіри. Цей механізм усуває залежність оцінки від частки оплат [47, 48] і відсутність даних у реальному часі [49, 50].

*Відображення.* У картці майданчика вказано джерело даних («датчики», «сесії та спостереження», «дані відсутні») і час останнього оновлення. Клієнт більше не опитує сервер періодично: зміни доставляються через SignalR із підпискою на групу за географічною коміркою.

**Бронювання та керування сесією.**

*Бронювання.* Бронюється конкретне місце на платному майданчику. Подвійне бронювання виключається на рівні СУБД обмеженням `EXCLUDE USING gist (spot_id WITH =, period WITH &&)`. Бронювання, яке очікує оплати, автоматично скасовується, коли закінчується відведений час (TTL). Тривалість TTL визначається на етапі проєктування. Це знімає невизначеність через проміжні статуси LiqPay [51] і розбіжність запасу місць [52].

*Оплата.* Інтеграція з LiqPay працює в режимі sandbox і включає:
- верифікацію цифрового підпису;
- ідемпотентну обробку callback-повідомлень;
- повторні спроби та автоматичний вимикач (circuit breaker) для викликів зовнішнього API.

*Паркувальна сесія.* Життєвий цикл сесії реалізовано скінченним автоматом Активна → Очікує підтвердження → Непідтверджена → Завершена. Перед завершенням оплаченого періоду водію надсилається push-сповіщення. На платних майданчиках із датчиками контролюється перевищення оплаченого часу: діє пільговий період, після нього здійснюється донарахування за підвищеним тарифом, а за наявності заборгованості нові бронювання блокуються.

**Подієве нарахування бонусів.** Сервіс Loyalty споживає доменні події реєстрації, оплати, скасування та підтвердження спостережень. Ручне сканування QR-коду [53] і стороння платформа [54] більше не потрібні. Бонусні бали нараховуються за спостереження, підтверджені іншими водіями або датчиками. Так формується зворотний зв'язок, що стимулює водіїв надавати достовірні дані для моніторингу (див. «Гібридний моніторинг зайнятості»). У разі скасування операції бонуси сторнуються компенсуючою транзакцією.

**Побудова маршруту.** Сервіс Parking Catalog розраховує маршрут від поточного місцезнаходження водія до обраного майданчика через API OpenRouteService. Координати водія обробляються лише для виконання запиту і не зберігаються.

### Функціональні вимоги (Core Features)

**Parking Catalog Service**
- **FR-01.** Відображати інтерактивну мапу паркувальних майданчиків, а саме:
  - виконувати геопошук у заданому радіусі (`ST_DWithin`, PostGIS);
  - кластеризувати маркери;
  - позначати кольором статус місць (вільне, зайняте, заброньоване, дані відсутні);
  - оновлювати статуси без перезавантаження сторінки через підписку SignalR.
- **FR-02.** Розраховувати й відображати маршрут від поточного місцезнаходження водія до обраного майданчика через API OpenRouteService.

**Occupancy Service**
- **FR-03.** Приймати події датчиків через MQTT 5.0 (QoS 1, TLS) і дедуплікувати їх за парою (`sensor_id`, `seq`). Контролювати heartbeat датчиків і публікувати зміни стану місць клієнтам через SignalR.
- **FR-04.** Оцінювати заповненість зон на майданчиках без датчиків за активними паркувальними сесіями та спостереженнями водіїв. Для цього перевіряти геолокацію автора, зважувати спостереження рейтингом довіри та знижувати їхню вагу з часом. Зазначати джерело даних у картці майданчика.

**Booking Service**
- **FR-05.** Бронювати місце на платному майданчику з виключенням подвійного бронювання обмеженням EXCLUDE на рівні СУБД. Автоматично скасовувати неоплачені бронювання після закінчення TTL.
- **FR-06.** Керувати паркувальною сесією:
  - реєструвати прибуття із заявленою тривалістю стоянки;
  - формувати контекстний запит після прибуття за маршрутом;
  - продовжувати сесію;
  - надсилати push-сповіщення перед завершенням сесії;
  - виконувати переходи автомата Активна → Очікує підтвердження → Непідтверджена → Завершена;
  - на платних майданчиках із датчиками контролювати перевищення оплаченого часу: пільговий період, донарахування за підвищеним тарифом, блокування нових бронювань за наявності заборгованості.

**Payment Service**
- **FR-07.** Ініціювати платежі LiqPay у режимі sandbox, формувати й верифікувати цифровий підпис [51]. Ідемпотентно обробляти callback-повідомлення. Виконувати повторні спроби та застосовувати автоматичний вимикач (circuit breaker) до викликів зовнішнього API.

**Loyalty Service**
- **FR-08.** Нараховувати вітальну знижку за реєстрацію та знижку до дня народження, застосовувати промокоди. Нараховувати бонусні бали за спостереження, підтверджені іншими водіями або датчиками. Сторнувати бонуси в разі скасування операції.

### Постановка задачі (технічне резюме)

Таким чином, метою кваліфікаційної роботи є проєктування та розробка хмароорієнтованої подієво-керованої платформи для вирішення задачі управління міським паркуванням: гібридного моніторингу зайнятості місць за даними датчиків, паркувальних сесій і спостережень водіїв, бронювання місць із виключенням подвійного бронювання, керування паркувальними сесіями, онлайн-оплати та програми лояльності. Платформа складається з шести сервісів, розгорнутих в Azure Container Apps, які обмінюються доменними подіями через брокер повідомлень і доставляють зміни клієнтам у реальному часі через SignalR.
